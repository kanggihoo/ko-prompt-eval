# 결정 기록

2026-11-19까지 정한 것입니다. 출처는 셋 중 하나입니다.

- **사용자:** 사용자가 직접 정한 것.
- **토론:** Claude와 Codex 토론에서 합의했고, 사용자가 반대하지 않은 것.
- **토론 + 사용자:** 토론에서 합의했고, 사용자가 검토해 확정한 것.

토론 요약 원문은 [`discussions/`](discussions/)에 있습니다. ID 앞 글자는 토론 출처를 뜻합니다. I는 [실행·증거·자동화 토론](discussions/2026-11-19-eval-automation.md), M은 [평가 지표 토론](discussions/2026-11-19-eval-metrics.md)입니다.

| D-11 | 증거의 정본은 repo 안의 실험 폴더 파일이다. 파일 계약은 [`implementation.md`](implementation.md) 2절 (I2, I14) | 토론 |

| D-15 | 단계는 `run` 뒤에 `metrics`, `judge`, `report`가 각각 `results.jsonl`을 읽는 구조다 (I7) | 토론 |

## 평가

| ID | 결정 | 출처 |
|---|---|---|
| D-30 | 두 task 모두 기준 질문은 "처음 이 답을 받았다면, 다시 묻게 된 부분을 이해할 수 있었겠는가"다. `rewrite`도 생성 때는 반응을 안 받지만 평가는 반응 기준으로 한다 (M1) | 토론 + 사용자 |
| D-31 | `rewrite` 고유 기준은 K-Humanizer의 의미 보존, 편집 절제, 자연스러움이다. "원문에 없는 내용 추가" 감점은 `rewrite`에만 적용한다. business 32건은 원래 기준을 쓰고, 유지율은 보존 대상 문단의 일치로 센다 (M5) | 토론 + 사용자 |
| D-32 | 자동 지표는 서술, 지시 준수, 실행 정보로만 쓰고 품질 점수에 넣지 않는다 (M7) | 토론 + 사용자 |
| D-33 | 사람 판정은 task 안의 두 변형을 같은 case, 같은 회차끼리 blind 짝으로 놓고 본다. 두 답을 동시에 보여 주고, 제시 순서와 A/B 위치를 기록한다. 출력별 이해 비율은 "재검토 판단"으로 해석한다 (I5, M2, M10) | 토론 (사용자에게 설명함) |
| D-34 | 판정 전에 "당시 막혔던 부분을 지금 설명할 수 있나"를 묻는 절차(M11)는 넣지 않는다. 출처 날짜만 case 결과에 붙인다 | 사용자 (토론 합의를 뺌) |
| D-35 | judge는 답 하나를 한 번에 채점한다. `rewrite` 답도 "의문이 풀렸나"와 "잘 고쳐 썼나"를 한 호출에서 본다. 토론에서는 두 호출로 나누기로 했으나, 기준이 섞일 위험이 확인되지 않은 추측이라 뺐다 (M13) | 사용자 |
| D-36 | judge는 사람 판정과의 일치를 확인하기 전에는 판정 근거로도, 거르는 용도로도 쓰지 않는다. 원래 `prior_answer`는 judge 검증의 정답 예시로 쓰지 않는다 (I6, M4) | 토론 |
| D-37 | 단일 합격선은 두지 않는다. 승·패·동률과 비용을 함께 보고 사람이 판단한다 (M8). 9건에서 6/9 이상이 우연히 나올 확률은 약 25% | 토론 |
