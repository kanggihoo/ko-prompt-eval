# 평가 방법

출력이 "잘했는지"를 무엇으로 재는지 정리한 문서입니다. 결정의 출처는 [`decisions.md`](decisions.md) D-30~D-37, 토론 원문은 [`discussions/2026-11-19-eval-metrics.md`](discussions/2026-11-19-eval-metrics.md)입니다. 토론에 있던 task 사이 비교(M6)는 사용자 결정(D-4)으로 빠졌습니다.

## 1. 기준 질문

두 task 모두 같은 질문으로 평가합니다.

> 처음 이 답을 받았다면, 다시 묻게 된 부분을 이해할 수 있었겠는가?

`commit-log-flush`라면 "이 답을 읽고 로그 flush가 무엇인지 알 수 있는가"입니다.

`rewrite`는 답을 만들 때 사용자 반응을 받지 않습니다. 그래도 평가는 반응 기준으로 합니다. 반응을 모른 채 글만 다듬어서 의문이 풀리는지가 `rewrite`에서 알고 싶은 것이기 때문입니다. `rewrite`가 원문을 잘 고쳤는지는 3절의 고유 체크로 따로 봅니다.

## 2. 사람 판정

주 판정입니다. judge와 자동 지표는 보조입니다.

### 무엇을 읽나

task마다 핵심 변형 두 개의 답을 같은 case, 같은 회차끼리 짝지어 읽습니다.

| task | 짝 | 짝 수 |
|---|---|---|
| `reexplain` | `claude-md-defaults` 대 `explain-clearly` | 9건 × 3회 = 27 |
| `rewrite` | `claude-md-defaults` 대 K-Humanizer | 9건 × 3회 = 27 |

합계 54쌍, 출력 108개입니다. "없음"과 ste-ko는 이 판정이 끝난 뒤 선택으로 봅니다.

### 판정 순서

1. **case를 열 때.** 원래 질문과 반응을 보여 줍니다. `gap`은 보여 주지 않습니다(D-6).

2. **짝마다.** 두 답을 한 화면에 함께 보여 줍니다. 어느 쪽이 어느 변형인지는 가리고, A/B 위치는 무작위로 정해 기록합니다(D-33).
   - **각 답의 이해 판정:**
     - 의문을 설명할 수 있음
     - 핵심 일부가 빠져 다시 물어야 함
     - 의문이 그대로 남음
   - **중요 사실 오류:** 있으면 문장, 근거, 확인 불가 여부를 적습니다. 이 표시는 이해 판정과 따로 기록합니다. 예를 들어 `deploy-lock` 원답이 "구현은 아직 없으니 확인 못 한 부분"이라고 한 것을 출력이 확정으로 바꾸면, 읽기는 쉬워져도 정확성은 나빠진 것입니다. 두 성질을 한 값으로 합치면 어느 쪽 문제인지 잃습니다.
   - **짝 선호:** `A / B / 동률 / 둘 다 불충분`.

3. **기록:** `human.jsonl`에 남깁니다. 필드는 review ID, 출력 ID, 판정, 오류 표시, 메모, 제시 순서입니다.

### 해석할 때

- 한 case를 여러 번 읽으면 앞의 답에서 배운 것이 뒤의 답을 쉬워 보이게 합니다. 짝 안의 두 답은 같은 상태에서 비교되므로 짝 선호는 비교적 공정합니다.
- 반면 답마다 매긴 이해 판정의 비율은 "처음 읽고 이해했다"가 아니라 "여러 번 읽은 뒤의 판단"입니다. 보고할 때 그렇게 적습니다(D-33).
- **성공:** 이해 판정이 "의문을 설명할 수 있음"이면서 확인된 중요 오류가 없는 답입니다.
- **case 승자:** 3회 중 과반을 이긴 변형입니다. 실패한 호출 때문에 과반을 판정할 수 없으면 미확정입니다. 실패한 호출을 빈 답으로 넣어 패배로 세지 않습니다(D-17).

## 3. LLM judge

judge는 사람 판정과 얼마나 일치하는지 확인하기 전에는 판정 근거로도, 사람이 볼 답을 거르는 용도로도 쓰지 않습니다(D-36).

### 공통 조건

- 생성 모델과 다른 계열의 모델을 씁니다.
- 변형 이름과 task 이름은 숨깁니다.
- JSON으로 답하게 하고, 파싱에 실패하면 그 행을 실패로 남깁니다.
- 판정마다 근거 구절을 인용하게 합니다.

### ① 이해 체크 (두 task의 모든 답)

- **입력:** 질문, 직전 답변, 반응, 익명 출력. 사용자가 검토한 `gap`이 있으면 함께 줍니다.

| 항목 | 값 | 정의 |
|---|---|---|
| `answers_reaction` | 예 / 부분 / 아니오 + 근거 | 반응이 묻거나 오해한 지점에 직접 답하는가. 반응 문장과 출력 문장을 인용 |
| `defines_target` | 예 / 아니오 / 해당 없음 | 반응이 특정 용어나 개념을 가리킬 때만, 그것을 풀었는가. `rebase-shared`("이해가 안되는데")처럼 대상이 특정되지 않으면 해당 없음 |
| `new_unexplained` | 목록 | 이해에 필요한데 설명 없이 새로 끌어들인 용어 |
| `major_error` | 없음 / 있음(근거) / 확인 불가 | 직전 답변의 맞는 내용을 틀리게 바꾸거나, 근거 없는 새 주장을 했는가. 원문에서 도출되는 쉬운 풀이는 오류가 아님 |
| `gap_filled` | 예 / 아니오 | 검토된 `gap`이 있는 case에서만 |
| `korean_naturalness` | 1 / 3 / 5 | `reexplain` 답에만. K-Humanizer 기준 |
| `answer_first` | 예 / 아니오 | `reexplain` 답에만. 진단용. 5줄 규칙과 `explain-clearly`가 모두 지시하는 것이라 품질로 해석하지 않음 |

### ② `rewrite` 고유 체크 (`rewrite` 답만)

- **입력:** 원문(직전 답변), 편집 요청, 익명 출력. 반응은 주지 않습니다.

| 항목 | 정의 |
|---|---|
| `meaning_fidelity` | 원문의 주장, 조건, 확신 정도, 수치를 지켰는가 (K-Humanizer) |
| `edit_discipline` | 필요 없는 변경을 하지 않았는가. 원문에 없는 실질 주장은 감점. 원문에서 도출되는 쉬운 풀이는 허용 |
| `korean_naturalness` | 문장 사이 연결을 포함한 자연스러움 (K-Humanizer 1·3·5) |

①과 ②를 따로 부르는 이유가 있습니다. 한 번에 부르면 judge가 반응까지 보고, "flush 설명이 없다"는 이유로 `edit_discipline`까지 깎을 수 있습니다. 원문에 없는 설명을 넣지 않은 것은 고쳐 쓰기로서는 올바른 행동입니다(D-35). 그 대신 `rewrite` 답 하나에 judge 호출이 2회 들어서, 핵심 출력 54개 기준으로 54회가 늘어납니다.

### `business_korean.v1` 32건 (나중에)

- 생성 모델에는 원래 입력 지시만 주고, `grading`은 judge에만 줍니다.
- K-Humanizer 원래 기준을 그대로 씁니다. `expected_behavior_met`, `hard_failure`, 5개 항목입니다.
- `keep_unchanged` 7건의 유지율이 과잉 수정 지표입니다. 응답 전체가 같은지가 아니라 보존 대상 문단이 같은지로 셉니다. `bk_landing_003`처럼 보존과 설명을 함께 요구하는 case가 있기 때문입니다(D-31).
- 구성은 생성 22, 유지 7, 질문 3입니다.

### K-Humanizer rubric에서 가져오지 않는 것

- Red Flag "Adds a new fact…"를 `reexplain`에 적용하는 것. 정의와 원인을 더하는 것이 `reexplain`의 목적입니다.
- 비즈니스 외 도메인 체크.

### judge 검증

- 원래 `prior_answer`를 정답 실패 예시로 쓰지 않습니다. `deploy-lock` 원답에는 사용자가 다시 물은 구분이 이미 들어 있습니다. "내용이 있다"와 "사용자가 이해했다"는 다릅니다(D-36).
- 검증은 사람이 판정한 같은 출력으로 합니다. 5절 ④를 봅니다.

## 4. 자동 지표

품질 점수에 넣지 않고, 사람이 읽을 때 참고하는 서술용으로만 씁니다(D-32).

| 종류 | 지표 | 계산 |
|---|---|---|
| 서술 | 산문 어절 수 | Markdown 표식, 코드, URL을 빼고 공백으로 분할 |
| 서술 | 문장 수 | 명시한 분리 규칙의 추정치 |
| 서술 | 구조 | heading, list item, table, code fence 개수 |
| 서술 | 영문 비율 | 영문 문자 / 전체 문자 |
| 지시 준수 | 변형이 금지한 표현 | 줄표 부연, "A가 아니라 B", 콜론 반전, "맞습니다" 오프너, 공감 멘트. 건수와 짧은 예시 |
| 지시 준수 | ste-ko lint | `--surface 대화 --no-vocab`. 규칙별 경고. 어휘 규칙은 "여러", "최근" 같은 평범한 단어도 잡아서 끔 |
| 실행 정보 | token 성분, 지연, `cost_usd` + `cost_source`, `tool_used` | [`implementation.md`](implementation.md) 2절 |

`explain-clearly`가 금지한 표현을 세는 지표는 `explain-clearly`가 지시를 잘 따랐는지만 보여 줍니다. 이것을 품질로 보고하면, `explain-clearly` 기준으로 `explain-clearly`를 채점하는 셈이 됩니다.

## 5. 집계와 보고

task마다 따로 냅니다. 순서는 다음과 같습니다(D-37).

1. **case 표:** case별 짝 승·패·동률·미확정. 원래 답변의 출처 agent와 모델, 출처 날짜를 붙입니다. 소표본이라 모델 계열별 순위는 만들지 않습니다.
2. **변형 표:**
   - `이해됨 / 검토 출력`
   - `이해됨이면서 중요 오류 없음 / 검토 출력`
   - 미검토 수, 확인 불가 수
   - 확인 불가가 있으면 성공 수 범위. 예: 검토 12, 이해됨 8, 확인된 오류 1, 확인 불가 2 → 성공 5–7. 신뢰구간이 아니라 확인 불가를 어떻게 처리하느냐에 따른 차이입니다.
3. **성공 1개당 비용:** 같은 case·repeat 집합에서 시도 비용 합계를 성공 수로 나눕니다. `cost_source`를 표시합니다. 비용 미보고나 성공 0이면 생략하고 이유를 적습니다.
4. **judge 신뢰도:**
   - 사람과의 짝 방향·동률 일치
   - 사람이 표시한 중요 오류를 judge가 놓친 수
   - 판정 건수
   - `answers_reaction` × 사람 이해 판정 교차표
   - 이것이 확인되기 전에는 judge 수치를 결론에 쓰지 않습니다.
5. **실행 상태:** `완료 쌍 / 계획 쌍`, 변형별 실패 수.

단일 합격선은 두지 않습니다. 두 변형이 실제로 같아서 동전 던지기처럼 이긴다고 해도, 9건에서 6건 이상 이길 확률은 약 25%(130/512)입니다. 7건 이상은 약 9%, 8건 이상은 약 2%입니다. 숫자 하나로 정하지 않고, 승·패·동률과 비용을 함께 보고 사람이 판단합니다.
